# AGENTS.md

Rules for AI agents (zer0ne itself, Claude Code, Codex…) working in this repository.

## What lives where

- `app/` — the Electron main process. `main.js` (app lifecycle, tray, the page bridge and its
  permissions in `permissions.js`), `engines.js` (one window: its start page, one engine process
  and page view per project, activation, retirement, crashes), `ops.js` (what engines ask the app
  for: dialogs, clipboard, links, folders, applet windows, notifications), `glass.js` and
  `desktop-icons.js` (Liquid Glass), `keychain.js` (the engine key), `preload.js` (the only bridge
  pages get: `window.__zcShell`).
- `app/desktop-ui.js`, `app/desktop-glass.js` — the desktop layer. The engine host inlines them
  into every engine page (`host/host.js`); the start page loads `desktop-ui.js` directly.
- `host/` — runs one engine: `main.js` (the stdio protocol with the app), `host.js` (the engine
  harness), `desktop-shim.js` (the `vscode` API the engine is written against).
- `engine/src/` — the coding engine (TypeScript). `engine/out/` is generated by
  `npm run engine`; never edit it by hand.
- `engine/media/` — the UI. `ui/` — the start page. New page features go in their own script
  (`settings-*.js`, `chat-*.js`: an IIFE exposing `window.X.create(deps)`), not into `chat.js` or
  `settings.js`; list it in the page's scripts in `engine/src/remote.ts` and in
  `engine/test/page-scripts.js`.
- `engine/eval/cases/` — the benchmark tasks (shipped); `engine/eval/reference.json` holds a
  correct fix for every hidden grader, and the engine suite checks each grader against it.

## Guardrails

### Release output

Build only into the configured release folder, `dist/win-unpacked`. The installer
(`npm run installer`) wraps that folder into `dist/zer0ne-Code-Setup-<version>.exe`. Do not create
alternate release folders or build copies.

### Committing is prohibited

Never commit, amend, push, tag or rewrite history, and never stage files, unless the user
explicitly asked for that exact action in the current message.

### Pages get nothing beyond the bridge

Pages run with context isolation and the sandbox; their only access to the app is
`window.__zcShell.invoke`. A new command needs an entry in `app/permissions.js` for the page that
may use it, and the app identifies the caller by its webContents, never by what the page says.

### Verify before you claim done

- `npm run check` — the engine type-checks, the app's JavaScript parses, and the architecture
  rules hold (`scripts/check-architecture.js`: part boundaries, module-free pages, the bridge,
  sandboxed page views, permissions matching the shell's dispatch), and `npm run lint` (Biome,
  bug-class rules only, never rewrites files; `biome.json` says which).
- `npm test` — app tests, including the real app on a temporary data folder (`test/app-smoke.js`)
  and `scripts/check-shipped.js` (exact dependency versions; everything shipped code loads is in
  the package). Both runners start suites without API keys or tokens in the environment.
- `npm run test:engine` — the engine's suite.
- `build.bat test` — the same against the packaged app.

### Keep CHANGELOG.md current

Every user-visible change gets a concise entry under `Unreleased` in `CHANGELOG.md`, in the same
change that made it. Nothing for build scripts, tests or private internals.

### Documentation speaks to app users

`README.md` explains the app and how to build it, not the architecture. Document the code in code
comments; comments state constraints the code cannot show, nothing else.
